# project-state 变更记录

## 2026-10-29 0.7.0：卡片跟着现状走——来源会话有后续时提醒 AI 自己更新

**起因**：用户回顾 pstate 时发现“明明 codex 或者 claude 已经做过了，却还是旧记录”。核对 4 张 open 卡：Rust 编译内存那张，10-22 记卡后同一会话次日用户回“那就1，2”，AI 已改全局 Cargo 配置、实测并写进 serial-split HANDOFF，卡仍停在“未见批准”；LCD 识别那张，同一 Codex 会话当天已抽帧跑出两版结果，卡仍写“尚无图片输入”；T04 那张后来试过删沙箱目录未记。共同点：卡在会话中途记下，同一会话继续干活，没有任何东西回写卡片，回顾的 AI 又把旧停点当现状报出。用户定的口径：“至少得提醒吧。ai自己肯定知道任务算不算做完。他自己打勾。然后和我说一下。”
**改成**：
- 新钩子 `hook-prompt`（Claude 与 Codex 的 UserPromptSubmit）：当前会话是 open/decided 卡的来源时，每轮开头注入卡片标题、ID、rev、最后更新时间，提醒做完就 done（带证据）、有进展就 set、改了告诉用户。只读事项库，不解析日志。
- `thread list/show` 增加 `last_touched`；open/decided 卡增加 `followups`（每个来源会话在 last_touched 之后的原生用户消息条数与最后时间）和 `possibly_stale`。日志修改时间不晚于 last_touched 时不解析；日志缺失记不可读、不算过期。
- skill 新增“卡片跟着现状走”：回顾时先读后续消息、自己 done/set，再给用户看。
**没选的路**：
- Stop 钩子每轮拦一次逼 AI 判断：每轮多一次续跑，卡片多的会话代价大；先用每轮注入，若实际仍被忽略再升级。
- 后台 sweep 自动改卡片状态：判断“算不算做完”需要读懂当轮工作，交给正在干活的 AI；后台只发现、不写事项状态的约定不变。
- 按 paths 查 Git 判断别的会话做掉的事：现有卡多数没填 paths，效果有限，先不做。
- 只看来源会话日志的修改时间：Claude 会话里钩子注入、工具结果也会改动文件，只数原生用户消息才不至于每张卡都报过期。
**影响**：两平台 manifest 升到 0.7.0，插件钩子新增 UserPromptSubmit，需刷新缓存后新会话生效；list/show 会多读来源日志（真实库 3 张卡约 3.5 秒）。旧版读新版写的库不受影响（未改 schema）。

## 2026-10-28 0.6.0：任务目录记下所有干过活的会话（会话.md）

**起因**：用户说“还有pstate，创建好项目之后。关联那次会话”，追问口径时定为“都记”——所有在该任务里干过活的会话都关联，不只创建那次。会话原文由 hub 另行存档（只存本机、明文），但 pstate 要能独立登记。codex 三路评审指出：`take` 不经过 `claim` 会漏登记；transfer 只认 decided，转交成功后补记会被拒；Codex 已把旧会话压成 `.jsonl.zst`，pstate 历史读不到大部分老会话。
**改成**：
- 任务目录 `会话.md` 受管区是唯一事实源，身份 = 主机 + 平台 + 会话号 + agentId；同一会话再登记只合并标签，首次时间不变；区外人工内容原样保留，区内损坏报错不重建。
- claim / take 成功后自动登记；新命令 `link` 可补录历史会话、登记派出去的 Codex 等子 agent（两个会话环境变量同时存在时要求显式指定，防把子会话记成父会话）；release 不删登记。
- thread transfer 写入全部来源（立项前来源 + 事项号 + 锚点）和执行转交的会话；关联失败与转交结果分开回报，同一目标重跑只补记、不 reopen。
- pstate 历史读取支持 Codex `.jsonl.zst`（sessions 与 archived_sessions），截断的整份报不可读。
**没选的路**：
- PSTATE_HOME 下建全局关联 JSON 再渲染成 Markdown：多一份要保持一致的数据，搬家还要重绑定，当前规模不值得（codex 评审）。
- 把 hub 会话索引当关联事实源：索引允许删除重建，且会让 pstate 依赖 hub；hub 只从 `会话.md` 读出反向显示。
- 写进任务 README：持续追加会干扰正文、更易与人工编辑冲突，README 只放入口。
- 按 cwd、正文提及或改过哪个仓自动推断关联：会话常从公司仓启动再用绝对路径改个人项目，按 cwd 必然认错；首版只做显式登记，候选查找以后由 hub 侧手动做、确认后走 link。
- 同一 Codex 会话号的多个文件按行数取多的那份：真机 15 组同号文件互不为前缀，取长的会丢短文件独有的记录；改为都读、按内容去重。
**影响**：旧版（0.5.x）不认 `link` 与 source 新可选字段 host/agentId/start_dir；两平台 manifest、插件缓存与稳定活源须一起发布。认领与文件锁仍只覆盖 Claude Code，Codex 会话靠 link 登记。

## 2026-10-27 0.5.0：按“立项”与 Obsidian 分工，旧看板退役，认领改认 Obsidian 任务

**起因**：用户说“我目前的psate感觉和obsidian的agents.md有一定重合”。核对后重合只在“有哪些活”和“做到哪了”两层：pstate 旧看板条目、thread 停点与 Obsidian 项目/任务、README 当前状态、HANDOFF 并行跟踪同一件事，“任务”一词三义。实际用量：Obsidian 23 个项目，pstate 全机 3 条 thread、2 条旧条目（一条是 17 天未动、会话开始仍在注入的公司仓遗留）。用户同意按立项切开，codex 两轮审方案。
**改成**：
- thread 只管立项之前；新终态 transferred（已转交）：用户决定做并把动机、结论、未决问题写进 Obsidian `…/task/Tnn-名称/` 后，`thread transfer` 记下任务目录并退出活跃提醒。只允许从 decided 且那次 do 原话已核验；transferred_to 只能由 transfer 写，重开时清掉、历史留 log；transferred 不能直接 done。
- 任务防重：用户选择保留认领（“A”），认领对象改为 Obsidian 任务目录，存全局 `claims/task-claims.json`，与 git 仓无关——会话几乎都从公司仓 cwd 启动、用绝对路径改个人项目，按 cwd 定仓的旧 claim 本来就认错仓。`take <任务目录>` 只转这一项；文件占用仍按仓库，拦截提示给出带 `--cwd <被写文件所在仓库>` 的接手命令；release 两部分分别回报；会话结束清掉其认领。
- 旧看板小范围退役：`new`（含 --force）一律拒绝；旧条目 status 只读显示、`done` 收尾，不再注入。会话开始只在有别的活会话或别人的认领时注入现场。
**没选的路**：
- 交接后保持 decided 只加链接：仍计入默认列表、开始提示和联合页，等于继续并行跟踪（codex）。
- 立项即 `thread done`：立项只是开始做，不是完成，会混淆完成证据（codex）。
- 只改 AGENTS.md 不动 CLI：钩子仍会要求 new/claim、CLI 仍能建条目，退役不成立（codex）。
- 不再防“同一件事做两遍”、只留文件锁：用户选了保留认领。
- 把 23 个 Obsidian 项目导入 pstate、同步 README、扫描 HANDOFF 或做总看板：过度设计，二者记录的对象和阶段本就不同。
**影响**：旧版读到含 transferred 的事项库会拒读（不会改坏），两平台缓存与稳定活源须一起更新；locks.json 里旧的看板认领字段被忽略。任务认领仍只覆盖 Claude Code。

## 2026-10-22 0.3.0：接住当前想法，并从历史找回可继续的事项

**起因**：本批 HANDOFF 记录的用户需求是回忆以前聊过且确实有后续的事情，由用户决定是否继续。原来只有按仓库组织的施工待办，无法接住跨会话讨论、无仓库想法或涉及多个工程的同一件事。
**改成**：增加独立于工程的全局事项；当前 AI 主动收录实质想法，并读取有界历史正文、筛选归并为卡片。继续聊只恢复卡片，决定做只记决定，先放着可找回，不做了保留原话；完成要有证据，重开须用户原话。用户结论、AI 建议、历史停点与当前核实事实分开，保存后回读才报已记下。
**改成**：Claude/Codex 本地正文保留原生锚点；显式 seen 关联内容版本，扫描不等于已审。旧 tasks/locks 兼容，施工进度仍引用 HANDOFF；开始提示仅计数与入口。
**没选的路**：不把 repo 当事项身份，不将所有讨论自动变成承诺；不增加 GUI、额外模型或全量自动导入。session-sweep 仅借只读旧 state 提示，旧会话关闭不当作事项完成。当前版本不抽共享扫描库、不新增跨仓调用依赖；普通 discover 全读所选 roots、返回页有界，精确抽样用 files，不声称已有扫描缓存。
**影响**：正式事项库不自动迁入历史；公司事项不自动收录。Codex 锁仍未适配，历史样本和脚本验证不等于安装后钩子验证；发布进度见 HANDOFF。

## 2026-10-09 0.2.0：改成会话互斥锁 ＋ 待办看板，只管个人项目

**起因**：用户整理各文件职能时说"pstate和HANDOFF也是不一样的概念吧……HANDOFF是要接受正在干但没干完。PSTATE是干我同时要做的几件事"，又说"我当初涉及pstate就不是为了公司项目吧，我当时说过，公司东西我记得住，不需要。 pstate是为了达到一个类似互斥锁的功能吧"。翻记录核实：出生那句"有时候很容易冲突，和handoff"里的冲突确实指并发，当时提过认领锁，用户"没想好"交给 codex，codex 以"手写认领证明不了对方还活着"否掉，于是只剩交接，和 HANDOFF 重叠，职能说不清；0.1.1 又在用户说"公司的我记得住"（10-06，session-sweep 讨论）的第二天把本板定成"管公司仓"，两头对不上。用户要防的冲突是两种：两个会话同时改同一批文件、同一件事被两个会话各做一遍；撞上要"拦下来"，不是只提醒；v1 只做 Claude Code。
**改成**：
- 锁不靠手写认领，挂在会话进程上：写文件前由钩子按相对路径（跨 worktree 算同一个）登记占用，别的活会话占着就拦下，AI 停下问用户等还是接手（`take` 转移所有权）；进程没了、会话结束、改动并进 main 后自动释放，squash / cherry-pick 的用 `release`。
- 看板条目瘦成一行标题 + 状态 + 一句目标 + HANDOFF 路径，默认 `待办`，开工前 `claim`；进度只写 HANDOFF。
- 只在有蓝图的个人项目生效（`lock on|off` 可按仓库开关）；公司仓不加锁、`new` 默认拒绝；公司仓里遗留的两个任务照旧注入，用户说"暂时不动"。
- 没有条目但有别的活会话时也注入看板。
**没选的路**：
- 一会话一个状态文件、各写各的（原方案）：codex 指出检查与登记之间有竞态，两边能同时通过 → 改成仓库一份状态、短锁内原子读改写。
- 用"对方那边文件已经变脏"判冲突：对方写入已登记、还没落盘时会漏拦 → 登记即生效，在途写入照样互斥。
- `take` 只做"我忽略对方"：对方照样能接着写 → 改成转移所有权，并拦对方一次告知被接手。
- 闲置超时自动释放 / 自动接手：在途写入可能正等用户批准，日志不更新也不代表没人在干 → 只显示时间，由用户决定。
- Stop 时补查 shell 写入：事后才发现、分不清是谁写的、用户中断时不触发 → v1 不做，写进已知盲区。
- 按"公司仓路径前缀"排除来识别个人项目：worktree 能放在任何目录 → 改成按蓝图正向识别 ＋ 仓库开关。
- 一次把 Codex 也做了：用户说不用，Codex 钩子能不能写前拦截也待实测。

## 2026-10-07 0.1.1：写清和 HANDOFF / 记忆 / session-sweep 的分工，AI 主动建任务

**起因**：宏观复查用户九月底以来的担心，其中一条正是出生时那句"缺少项目记忆，或者说todo。有时候很容易冲突，和handoff"。翻真实记录：出生后一个任务都没建过，进度仍散在 HANDOFF、原生记忆和 session-sweep 里，没有一处说清谁管什么。codex 指出零使用的真正原因是"AI 主动记录"这条触发没落实（skill 写的是用户说"记个任务"才建），加上没有任务时它完全静默，不是工具本身没用。
**改成**（只改 skill 规矩，不改代码）：同一件事的进度只记一处——有 vibe-flow HANDOFF 的项目只写 HANDOFF，本板管没有 HANDOFF 的仓库（公司仓等）；原生记忆和金库不记进度；session-sweep 只是发现入口。在没有 HANDOFF 的仓库里，AI 判断一件事一个会话做不完时当场建任务并告诉用户一句。vibe-flow 0.20.1 §6 写了同样的口径。
**没选的路**：
- 停用 pstate、进度统一归 HANDOFF：公司固件仓不建 vibe 文档、没有 HANDOFF，跨 worktree 交接和"留着的未提交改动为什么不提交"仍要有地方记（codex 否决停用）。

## 2026-09-30 出生：多 worktree、多 AI 会话共用的任务交接板

**起因**：用户原话："我还发现一个问题，就是缺少项目记忆，或者说todo。有时候很容易冲突，和handoff。" 同一个固件仓库开了几个 worktree，Claude 和 Codex 先后或同时在里面干活：谁在哪个工作区改什么互相看不见，会话结束或压缩后下一个接手的要从零捋；"未提交改动留在哪个 worktree、为什么不提交""撤回项在哪"这类状态要么只在工作区里，要么塞进了记忆，过几天就过期还被自动注入，误导后来的会话（其中一条"真实基线在某 worktree"时该 worktree 已不在 git 登记里）。
**改成**：仓库外本机目录按 git common dir 存一份任务板，一个任务一个 `.md`；git 现场（各 worktree 分支、未提交改动数）每次现算，人和 AI 只写目标、停在哪 / 下一步、阻塞、为什么保留改动；做完移出活跃视图；Claude Code 与 Codex 会话开始时有活跃任务才自动注入。
**没选的路**：
- 一张所有 AI 都去改的 Markdown 大表（进行中 / 待办 / 未提交状态 / 交接四块）：Codex 评审指出一张表扛不住"git 事实、交接意图、并发锁"三件事，而且多会话整页覆盖会互相吞掉更新 → 改成一任务一文件 + git 现算。
- 放进 hub 金库 shared/memory：进度变得太快，进了长期记忆的同步和注入链路就会留下过期副本。
- 放在仓库 git common dir 下：可行，但把日常状态塞进 git 管理目录，工具和沙箱可能限制读写，退为第二选择。
- 认领 / 文件级锁：手写认领证明不了对方还在干活，比没有更误导；`git worktree lock` 只防工作区被删除移动，防不了改文件。v1 靠"不同的活分 worktree"。
- Codex 提的完整版（每轮提问检测变化、写入前闸、带版本号的统一更新入口、Stop 时强制补交接）：第一版偏重，先不做；Stop 检查等跑一阵看交接会不会漏写再定。
- 只在 AGENTS.md 写一句"开工先读"：写了 AI 也不一定照做，改用会话开始钩子注入。
**影响**：现有记忆里的进度类条目（批次进度、公共层改动不提交、协议改动基线在某 worktree 等）应迁成任务后从记忆下架，否则新旧两处会互相矛盾。
