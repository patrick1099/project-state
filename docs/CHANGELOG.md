# project-state 变更记录

## 2026-09-30 出生：多 worktree、多 AI 会话共用的任务交接板

**起因**：用户原话："我还发现一个问题，就是缺少项目记忆，或者说todo。有时候很容易冲突，和handoff。" 同一个固件仓库开了几个 worktree，Claude 和 Codex 先后或同时在里面干活：谁在哪个工作区改什么互相看不见，会话结束或压缩后下一个接手的要从零捋；"未提交改动留在哪个 worktree、为什么不提交""撤回项在哪"这类状态要么只在工作区里，要么塞进了记忆，过几天就过期还被自动注入，误导后来的会话（其中一条"真实基线在某 worktree"时该 worktree 已不在 git 登记里）。
**改成**：仓库外本机目录按 git common dir 存一份任务板，一个任务一个 `.md`；git 现场（各 worktree 分支、未提交改动数）每次现算，人和 AI 只写目标、停在哪 / 下一步、阻塞、为什么保留改动；做完移出活跃视图；Claude Code 与 Codex 会话开始时有活跃任务才自动注入。
**没选的路**：
- 一张所有 AI 都去改的 Markdown 大表（进行中 / 待办 / 未提交状态 / 交接四块）：Codex 评审指出一张表扛不住"git 事实、交接意图、并发锁"三件事，而且多会话整页覆盖会互相吞掉更新 → 改成一任务一文件 + git 现算。
- 放进 hub 金库 shared/memory：进度变得太快，进了长期记忆的同步和注入链路就会留下过期副本。
- 放在仓库 git common dir 下：可行，但把日常状态塞进 git 管理目录，工具和沙箱可能限制读写，退为第二选择。
- 认领 / 文件级锁：手写认领证明不了对方还在干活，比没有更误导；`git worktree lock` 只防工作区被删除移动，防不了改文件。v1 靠"不同的活分 worktree"。
- Codex 提的完整版（每轮提问检测变化、写入前闸、带版本号的统一更新入口、Stop 时强制补交接）：第一版偏重，先不做；Stop 检查等跑一阵看交接会不会漏写再定。
- 只在 AGENTS.md 写一句"开工先读"：写了 AI 也不一定照做，改用会话开始钩子注入。
**影响**：现有记忆里的进度类条目（批次进度、公共层改动不提交、协议改动基线在某 worktree 等）应迁成任务后从记忆下架，否则新旧两处会互相矛盾。
